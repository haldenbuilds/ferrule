What is in it

Nine components, in two halves

The first half is about getting a system installed and proving it landed. The second is about the work the installed system does, which is a different question and the one nobody usually has an instrument for.

Landing it 4 components
  1. 01 Session control What a session may write, what patterns stop a write, and proof your hooks actually fire rather than merely being configured.
  2. 02 Lane control Firing work nobody is watching, and knowing honestly whether it finished. The worker cannot write its own completion flag.
  3. 03 Capability authoring Scaffolds for a capability and a worker, plus a held-out case set graded on outcomes rather than wording. A case set that cannot fail is refused.
  4. 04 Install layer Landing a package in an environment that is not yours: a plan-then-apply runner that will not write outside its root, a collision resolver that stops rather than guesses, and a certifier that proves it can fail first.
The work it does 5 components
  1. 05 Claim compiler You declare each thing the finished system should do. It compiles every declaration into a check that can fail, runs it against the artifacts your system leaves behind, and reports which of your claims are asserted with nothing watching them.
  2. 06 Dead-end linter Reads a workflow you declare and names the states nothing reaches, the states with no way out, the endings that report success with no artifact, and the graph that cannot finish by any route. It runs nothing, so it is usable before the first unattended fire.
  3. 07 Dry-run lab Generates an adversarial input set from a shape you declare and runs your handler against every one of them, inside a context whose effects refuse and record. It reports which inputs broke it and what it would have touched.
  4. 08 Transcript auditor Grades a run's transcript against a rubric you write, and names the lines it failed. It ships no opinion about what a good run looks like: every line graded comes from your own file.
  5. 09 Runbook compiler Reads a verification verdict and compiles the handover document from what was actually built and proven. It cannot carry an all-clear the verdict did not earn.

Also in the download

Two worked examples, start to verified finish. Trap sheets for the two components with the most traps. An install manual, and an instructions file written for your own assistant to follow.

What it reports

The verification harness

One command. It prints one verdict and returns an exit code you do not have to interpret twice.

  1. PROVEN Every installed component proved its checks against your own configuration.
  2. EXAMPLE_PROVEN Everything passed against the examples that ship here.
  3. NOT_YET A step only you can do is still open.
  4. BROKEN A check failed and the output names which.
  5. CANNOT_VERIFY It could not run at all. CANNOT_VERIFY is never a pass.

A fresh download reports EXAMPLE_PROVEN, and that is correct

Copying an example and changing nothing keeps it there, on purpose. The gap between "this code works" and "this is configured for me" is the gap worth having a word for, and only one of the two is worth trusting unattended work to.

What is not in it

Item by item

  • No cross-component routing, dispatch or capacity layer. The nine components are parts. The layer that decides which worker takes which job is not in this release and is not coming in a later one. The parts are yours; the conductor is not.
  • No values tuned to your work. Every file is generic by construction, and everything specific comes from files you fill in.
  • No agent that acts inside your environment. Nothing here installs itself. Your own assistant does the installing, on your machine, under your hand.
  • No support entitlement, no onboarding call, no setup review. The test applied to every item in this release: could this be delivered by a file with nobody on our side?
  • No opinion about what a good run looks like. The transcript auditor ships no rubric and the claim compiler ships no claims.

This boundary ships as a file inside the download, not as a policy page on a website, so you, a reviewer, and whoever cuts the next release all read the same line.
