Free release 01

The FERRULE Harness Audit, Release 1.0

What your unattended setup can and cannot prove

A read-only look at your coding-agent setup. It runs on your machine, against your own configuration, and reports three things: what you have, what you do not have, and what it could not see.

It measures. It does not claim. The failure it is built around: a hook that is wired into your settings, whose script exists on disk, and that has never once fired is indistinguishable from a working one by reading the configuration. Reading the configuration is what every setup checker does. This one separates checked-and-clear from could-not-check, and prints the third category first.

The 23 checks, by group

  1. 01 Discovery Harness detected / Instruction file / Settings file / Settings parse 4 checks
  2. 02 Hook wiring Lifecycle coverage / Declared hooks point at files that exist / Hook paths that depend on a variable / Hook timeouts 4 checks
  3. 03 Run evidence Evidence that hooks actually run / Evidence freshness 2 checks
  4. 04 Permission fences Refusal rules / Blanket permissions / Secret-shaped files / Names that mention credentials / Confirmation rules 5 checks
  5. 05 Unattended-run wiring Completion signal / Signal directory / Run log 3 checks
  6. 06 Instruction hygiene Instruction file size / Pointers in the instruction file / Competing instruction files 3 checks
  7. 07 Capability inventory Capability inventory / Capability usage 2 checks

What comes out, and the order it prints in

The report is written to your own directory as a readable page and as the same result in data form, so two runs can be compared. The order below is the order it prints, and the first section is first on purpose.

  1. COULD NOT SEE The check ran and could not reach its evidence. An unknown is not a pass, and treating it as one is how a setup gets called healthy while it is not.
  2. BROKEN Something is declared but is not working. These are the findings where the setup and the intent disagree.
  3. MISSING A control that is absent. Absent is not the same as broken. Some of these you may not want, and that is a decision, not a defect.
  4. WORTH KNOWING Not a defect. A property of the setup that tends to matter later.
  5. CLEAR Checked, and found in place.

Prove the tool before you trust it

It ships with a self-test that builds two harnesses in a temporary directory: one with defects planted on purpose, one with the same shape and none of them. It then asserts that the engine reports exactly the planted list against the first and none of that list against the second. A checker that always fires is as useless as one that never does, and only running the broken half would hide that.

What it deliberately does not do

  • It reads configuration and files. It does not watch a live session, so it cannot prove a hook fired today. It can prove that one left a trace, and that a declared one points at a file that is not there.
  • It checks one target per command, the script the interpreter is told to run. Arguments passed to that script are not followed.
  • It matches credential-shaped names, never contents. A harmless file with a risky name gets flagged; a risky file with a harmless name does not.
  • Counts of capabilities are counts of files and folders. It does not judge whether any of them are any good.
  • A setup it has no profile for is reported as not detected, never as clean.
  • It runs nothing and sends nothing. There is no subprocess, no shell and no network call in the engine, and it writes only inside the output directory you name.

Those limits are printed inside every report it writes, not only here. A limit that appears once is a limit people read once.

Free release 02

The FERRULE Kit, Release 1.0

Three controls, each one proving it runs

An install kit your own coding assistant reads and builds from. You hand it the folder, it builds one mechanism at a time, and a self-check that ships inside the kit proves each one runs on your machine.

Each path ships exactly one mechanism, proved. Not a survey of the subject.

The three paths, and the failure each is aimed at

  1. 01 A scope gate Refuses a write outside what you declared, with a trace you can read back. Aimed at the hook that is wired up, whose script exists, and that has never once fired. 1 mechanism
  2. 02 A capability with a boundary A stated boundary and an eval that can actually fail. Aimed at the case set of nothing but positive cases, or the threshold nothing could miss. Both go green and neither is visible in the file. 1 mechanism
  3. 03 An unattended-run contract A completion signal that lands where the worker cannot write it. Aimed at the run that reported success to nobody who was watching, which is a claim it made about itself. 1 mechanism

Start in two minutes, before you install anything

It starts with a two-minute version: one pasted prompt, no install, no Node. You watch the mechanism work on your own screen before you build it properly.

Nine laws, complete on their own

The rules the three paths are built on, each stated in full, each with a worked generic example, and each naming its own ceiling in the same file. They need nothing installed. You can act on every one of them today, by hand.

Their index carries its own reading order: which three to read tonight if you are about to fire something unattended, which two if you are building a check, and which one explains the other eight.

Reading a law and having a machine that enforces it are different things, and the distance between them is what MOAT-FENCE.md is about.

What the self-check says, and when

  1. DEMO PROVEN Your first run says this, and that is correct. Each mechanism ran against the example that ships in the kit and did what it says.
  2. BUILD PROVEN Reached once you supply your own scope, your own capability and your own contract. The gap between the two words is the gap worth having a word for.

What it deliberately does not do

  • It is generic scaffolding plus a self-check, and nothing else. The kit ships a file that draws that line, item by item, so you can read exactly what you have.
  • Tuned values, populated pattern sets, denylist contents and live operating state are held back from every tier, including from people who pay. What a deeper package sells is your ability to author your own contents, with a check that proves yours works.
  • Each path ships one mechanism, not a survey of the class. Three paths, three mechanisms, and no fourth.
  • Your agent does the building. Nothing here installs itself, and nothing acts inside your environment on its own.
  • It verifies its own delivery and refuses to run on a partial download, which means an incomplete download stops rather than half-works.
