FERRULE

Harness Audit, published source

A read-only look at your coding-agent setup. It reports what you have, what you do not have, and what it could not see. It measures. It does not claim.

This is the whole engine, in the open, under MIT. Read it first, then run it against your own machine. Node 18 or newer, no packages, no install step.

What it reports

The third column is the point

Could not see is not a pass

Most setup checks return green or they return red. This one returns green, red, and could not see, and it prints that third category first.

The reason is the single failure the tool is aimed at. A hook that is written into your settings file, whose script exists on disk, and that has never once left a trace is indistinguishable from a hook that never runs. You cannot tell those two apart by reading the configuration, and reading the configuration is what every setup checker does. This one separates checked-and-clear from could-not-check, and refuses to add the second to the first.

The five verdicts, in the order the report prints them

  • Could not see The check ran and could not reach its evidence. Printed first, because each line is a question about your setup that is currently open.
  • Broken Something is declared but is not working, or a fence you appear to want is not in place. The configuration and the intent disagree.
  • Missing An absent guardrail. Some of these you will not want, and deciding that is a legitimate outcome.
  • Worth knowing A property, not a defect.
  • Clear Checked and in place.

23 checks, in seven groups: discovery, hook wiring, run evidence, permission fences, unattended-run wiring, instruction hygiene, and inventory. Where a hook path is built from a variable, the result is reported as could-not-see, never as a pass. A setup the tool has no profile for is reported as not detected, never as clean.

A finding is not an instruction. Several of them describe things a small project should not bother with. The value is that the decision becomes yours instead of accidental.

Run it

Three lines, no install

Node 18 or newer. Nothing else

  • node harness-audit.mjs --project . --out ./audit-out Audits the current project and writes two files into ./audit-out: the report you read, and the same result as JSON for diffing between runs.
  • node harness-audit.mjs --redact Replaces your paths with placeholders in both the report and the JSON record, so a run can be shared.
  • node harness-audit.mjs --self-test Builds two harnesses in a temporary directory, one with defects planted on purpose and one with the same shape and none of them, then asserts the engine reports exactly the planted list against the first and none of it against the second. A checker that always fires is as useless as one that never does.

Exit codes: 0 it ran, 1 it ran and your --fail-on level was met, 3 it could not run and said why. On Windows PowerShell the same commands work unchanged.

The posture

Five lines you can check rather than trust

The engine is one readable file

  • Reads Your configuration files, your instruction files, and file names and timestamps under your project.
  • Runs Nothing from your project. No shell, no eval. The one subprocess in the file belongs to --self-test, which re-runs this same file with Node so the self-test grades the production path rather than a copy of it.
  • Sends Nothing. There is no network call. Search the file for fetch, http and socket: the only hit is the header line stating that none are there.
  • Writes Two files, into --out, or into the current directory if you do not pass it. Nothing else on disk is touched.
  • Opens Never a file it flags as credential-shaped. It matches on the name, stops there, and reports the path only. A harmless file with a risky name gets flagged; a risky file with a harmless name does not.

These are stated so you can check them rather than take them on faith, which is the reason the engine ships as a single file you can read in one sitting.

Delivery

It verifies itself before it reads anything

Six files, plus a manifest that cannot list itself

MANIFEST.json names the other six shipped files with their byte lengths and SHA-256 digests, and the tool refuses to run if any of them has moved. The check happens before configuration is read, so a package that arrived incomplete stops with exit 3 and a reason rather than auditing you from a half-delivered engine.

A manifest cannot carry its own hash, which is why the count is six plus the manifest. The self-test covers this path in both directions: it asserts a malformed manifest refuses, and that a package missing a listed file refuses.

Limits

What it cannot tell you

Stated here as well as in every report

A limit that only appears in the output is a limit people read once.

  • It reads configuration and files. It does not watch a live session, so it cannot prove a hook fired today. It can prove that one left a trace, and that a declared one points at a file that is not there.
  • It checks one target per command, the script the interpreter is told to run. Arguments passed to that script are not followed.
  • The ignore-file check reads the ignore file in every directory between the file and your project root. It does not evaluate negation rules or the full pathspec grammar.
  • It matches credential-shaped names, never contents.
  • Counts of capabilities are counts of files and folders. It does not judge whether any of them are good.
  • It looks four directories deep from your project root and skips build and dependency folders.
